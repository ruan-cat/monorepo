## 5. 经验教训

下面 13 条都来自这次事故。前 6 条是用户的归纳，后 7 条是同一场写入里另外的机制。

### 5.1 质量参差不齐

同一实体下面，有的记忆是带真阳性、真阴性的 compare 实测，有的是把别的视角的方案字母抄进来的摘要。检索按实体和关键词返回，不按证据强度过滤。后来的 agent 分不清哪一条能当事实。

以后：共享记忆只收一条，而且只收用户点名要留的那一条。并行调研的过程结论留在各自 markdown。

### 5.2 假阳性

`filesModified` 会把正文里出现的文件名收进去。历史索引写明：`#6467`、`#6471` 把 `compare/...` 表达式记成了路径；`#6468` 混入设计稿里的 `watch.yaml`、`plan.md`、`AGENTS.md`；`#6472` 混入任务包和上游 changelog 的路径；`#6474` 混入只读过的旧报告路径。

以后：写入时手填真实改过的文件。写完用 detail 回读 `filesModified`。命令、表达式、只读引用出现在这个字段里，就删掉这次写入，不另写一条去解释它。

### 5.3 过于严格的误判

「发版是否包含该 PR」依赖 compare 的参数顺序。`compare/{TAG}...{MERGE_SHA}` 配 `ahead_by == 0`，和 `compare/{MERGE_SHA}...{TAG}` 配 `merge_base` 相等，是两种正确写法。把第一种的判据套到第二种的参数顺序上，会该触发时不触发、不该触发时触发。

一个视角把另一个视角的写法标成「方向错误、禁止采信」。这个禁止被写进新的记忆，比原始取数命令传得更远。

以后：跨目录引用判据时，连同参数顺序和判据一起抄，并回到原命令重跑。不在记忆里宣布别人的编号或判据作废。

### 5.4 错路径

活记忆把 Cursor 的文件写成 `cursor/02-cursor-schemes.md` 和 `cursor/03-cursor-capabilities.md`。磁盘上不存在这两个文件。Cursor 目录只有 `README.md`、`01-facts.md`、`02-schemes.md`。

WorkBuddy-ai 的 README 写明：该目录原名 `cursor/`，属身份误判，2026-11-23 已 `git mv` 到 `WorkBuddy-ai/`。记忆的 `filesModified` 停在旧路径。

以后：记忆里的路径必须是写完后在磁盘上 `Test-Path` 过的路径。目录改名时，先改记忆里的路径，或直接删掉旧记忆。不留「权威目录」指向不存在的文件。

### 5.5 相互上下索引依赖

`#6480`、`#6481` 用「权威目录」去指其他视角的文件，指到了不存在的 Cursor 文件名。图实体的观察列表里还挂着已经不在表里的 `#6466`。知识声明、证据卡、会话摘要各复述了一遍 observation 的结论。

只删 observation，声明、图、会话仍会在下次开工时把旧结论交出去。这次是把这些派生记录和 observation 一起物理删除。

以后：记忆正文不引用别的 observation 编号当依据。依据写仓库相对路径和章节。需要删一条主题时，按实体清 observation、声明、证据卡、图、会话，而不是只改一条的状态。

### 5.6 胡乱归档，越权标记别人的记忆

`#6479` 在自己的正文里宣布 `#6463`、`#6465` 以及其他编号「已归档、不要再引用」。这些编号不全是它写的。归档不删除正文。`status=all` 和按编号 detail 仍能读到旧结论，而且读到的是被别人判过的版本。

以后：一个 agent 只改自己写入的那一条的状态。不在 A 的正文里宣布 B 已归档。要让旧结论停止注入，用物理删除或用户点名的覆盖，不用归档标记代替删除。

### 5.7 字母编号没有目录锚点

「推荐方案 A」在三个视角里是三个方案。MiniMax 的方案 A 是本机只读轮询器。WorkBuddy-ai 的方案 A 是本地定时轮询。WorkBuddy 把本机轮询编成方案 B，又在另一份文档里编成方案 A。Cursor 的文件用方案 1、方案 2、方案 3，推荐方案 1。

记忆标题和正文如果只写「推荐方案 A」，下一个 agent 无法知道该打开哪个文件。

以后：跨目录只写实质名，或写「仓库相对路径 + 章节标题」。不把 A/B/C/D/E 写进共享记忆。

### 5.8 同一实体并发只追加

四个 agent 共用一个实体名。纠正旧结论的办法是再插入一条。于是出现成对的现行文本：`#6464` 与 `#6465`，`#6467` 与 `#6475`，`#6470` 与 `#6477`，`#6471` 与 `#6478`。检索会把一对都交出来。

以后：同一主题的共享记忆最多一条。要改，就改那一条，或先删再写。并行调研期间不写这唯一的一条。

### 5.9 过宽的 topicKey 会改写别人的行

`#6463` 的 topicKey 就是实体名 `about-agent-watch-gh-pr-as-hooks`。存储实现按「同一项目 + 同一 topicKey」更新已有行。后来的写入如果带上这个 topicKey，会覆盖这一行，而不是新增。

以后：topicKey 用「视角目录 + 这一条的用途」，不用裸实体名。没有把握时不传 topicKey。

### 5.10 记忆会自动注入，markdown 不会

四个目录里的方案冲突，要打开对应文件才看得到。同一实体的记忆会在另一个 agent 搜索或读取项目上下文时进入提示词。用户可以接受 markdown 各自冲突。共享记忆库里的冲突会被当成已经核对过的事实。

以后：调研阶段的默认产物是该 agent 自己的 markdown 目录。Memorix 只在用户明确说「写入这一条」之后写，并且只写这一条。

### 5.11 删除行不回收编号

`#6466` 从 `observations` 消失之后，下一号仍是更大的号。删除 `#6463` 至 `#6482` 之前，`next_id` 已是 `6483`。若只删行，下一号仍是 `6483`，中间留下空洞，旧编号也不会复用。

这次要让下一号从 `#6463` 开始，做了两件事：把 `meta.next_id` 写成 `6463`，然后重启进程。重启前，活进程内存里的下一号可能仍是 `6483`，因为它取内存值与磁盘值中的较大者。重启后进程从磁盘重新读取，复读结果是最大号 `6462`、下一号 `6463`。

以后：要回收编号，先确认该号以上没有要保留的行，再改 `next_id`，再重启 Memorix 进程，再复读 `MAX(id)` 和 `next_id`。不把「行已经删了」说成「下一号会从缺口重新长」。

### 5.12 会话摘要是第二份记忆

Cursor 那次收尾写进会话 `sess-mwte3kpd-c1w847`。摘要里有调研结论和目录路径。observation 删了之后，下次 session 仍可能交出这份摘要。这次把该会话和 observation 一起删了。

以后：结束会话时的摘要只写「结论在哪个文件的哪一节」。不在摘要里重写方案、判据和别人的编号。清理一个主题时，把 summary 含该主题的会话算进删除清单。

### 5.13 订正正文如果复述错误原文，检索仍会命中错误原文

订正 `#6464`、`#6465` 时，文首写了「禁止当方案说明引用」，正文仍保留「推荐序 A→D→B→C」和两个不存在的文件名。全文检索按这些字符串命中，读者先看到的是这条订正，而不是磁盘上的 `cursor/02-schemes.md`。

以后：纠正一条记忆时，不把要废止的口号和错误路径再写一遍。正确的做法是删掉该条，或把正文换成只含真实路径的短句。废止说明写在 markdown，不写进会被检索的记忆正文。

## 6. 下次多 agent 写 Memorix 的硬边界

1. 并行调研的各自结论只进自己的目录。四个目录可以冲突。
2. 共享实体的 Memorix 写入要单独授权。授权时给出实体、类型、标题、正文要点、文件列表。未授权不写。
3. 一个主题只留一条共享记忆。第二条出现时，先停，让用户选留哪一条。
4. 不归档、不 resolve、不在正文里点名别人的 observation 编号。
5. `filesModified` 只填这次真正写入的文件。写完 detail 回读。
6. 方案用实质名或「路径 + 章节」。不用 A/B/C/D/E。
7. 判据带上 compare 的参数顺序。从别的目录搬来的判据，先重跑再引用。
8. topicKey 不含裸实体名。
9. 会话摘要不复述方案和判据。
10. 要让一批编号停止注入，物理删除 observation 及其声明、证据卡、图、会话，并按第 5.11 节处理 `next_id`。归档不算删除。
