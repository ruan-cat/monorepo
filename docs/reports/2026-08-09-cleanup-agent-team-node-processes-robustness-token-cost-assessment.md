# 2026-08-09 cleanup-agent-team-node-processes 健壮性与 token 成本评估

> Agent 工具：Codex Desktop 主代理，配合只读探索、健壮性审计和 token/分发审计子代理。
>
> AI 模型：主代理为 GPT-5 系列 Codex，当前运行时未暴露更细的部署标识；子代理审计使用 Terra low。未使用 Sol。
>
> 评估性质：本报告是只读技术评估，不修改技能实现，不执行真实进程终止，不提交或发布任何文件。

## 结论

当前 `cleanup-agent-team-node-processes` 不能笼统地称为“已经健壮”。更准确的判断是：仓库中的 `1.4.1` 源码已经具备中上水平的保守安全门禁，但用户日常调用的全局安装仍停留在 `1.3.0`，没有获得本轮 WorkBuddy 加固和模块化成果；与此同时，默认 dry-run 输出协议会生成数十万字符的全量 JSON，模型读取成本远高于脚本运行成本。

因此，我建议继续优化，但优化目标不是换语言，也不是继续扩大脚本架构。下一轮应优先解决三个问题：让默认输出变成低 token 的决策摘要、让仓库版本真正发布并同步到全局安装、修补两个与破坏性终止直接相关的 P1 安全缺口。完成这些工作以后，再决定是否继续拆分接近尺寸门禁的长函数。

如果用一句话概括：**源码安全基本盘已经形成，但用户入口、输出协议和少数终止门禁还没有闭环。**

## 评估范围与方法

本次评估同时检查了四个层面，避免只看源码后得出过度乐观结论。

第一，检查仓库源码中的 `SKILL.md`、PowerShell 入口、8 个 `scripts/lib` 模块和 Vitest 测试，重点关注 dry-run、Apply、WorkBuddy 分组、PID 身份复核、监听端口阻断、respawn 和台账输出。

第二，对比仓库源码与 `C:\Users\pc\.agents\skills\cleanup-agent-team-node-processes` 的实际全局安装，确认版本、文件数量和模块化状态是否一致。

第三，本次会话前段使用 stdout-only dry-run 进行多次只读测量，记录执行时间、目标进程数量、JSON 字符数和候选数量。执行入口为安装目录下的 `scripts/agent-team-node-cleanup.ps1`，没有传入 `-Apply` 或 `-OutputPath`，没有发生真实终止，也没有在工作区新增进程台账。前段审计只保留了观测区间，没有保留可逐次回放的精确样本数量和原始 stdout，因此这些数据只能作为同日历史观测，不应解释为持续可复现的基准测试。

第四，检查插件 manifest 与 `CHANGELOG.md`，判断仓库修改是否已经形成可追溯的发布和同步闭环。

Token 数量是成本估算，不是某个专有 tokenizer 的精确计费结果。报告同时参考字符数除以 4 的保守下界和中英文混合文本的启发式估算，目的是判断数量级和优化优先级，而不是声称精确到单个 token。独立复核代理的一次重跑曾遇到 `Get-CimInstance Win32_Process` 的 `AccessDenied 0x80041003`、退出码为 `1`，说明进程观察受宿主权限影响；主代理最终以 stdout 在本地解析、只回传摘要的方式重跑成功，但没有保留原始全量 JSON 字符数，因此没有用最终这次调用覆盖前段历史输出规模区间。

## 健壮性判断

### 仓库源码：中上，但不是高健壮

仓库 `1.4.1` 已经形成一组有效的保守防线：

- 默认是 dry-run，未显式传入 `-Apply` 时不会停止进程。
- fixture 快照不能进入真实 Apply，测试数据不会成为真实终止依据。
- 监听端口观察为 `unknown` 时会阻断候选，而不是把“无法确认”解释为“没有监听”。
- WorkBuddy Apply 使用冻结的停止计划，并在停止每个 PID 前复核 `PID + Name + CreationTime`。
- WorkBuddy 发现新 PID respawn 时只报告，不在同一轮继续追杀。
- Apply 台账路径被限制在系统临时目录；默认 dry-run 不落盘。
- 入口已缩短为约 91 行，主体拆为 8 个职责模块，明显优于原先约 1700 行单文件。

这些防线说明技能已经从“按进程名批量清理”升级为“基于归属证据和失败关闭策略的审计后清理”。这部分设计方向是正确的。

但高健壮性的标准不是“门禁数量多”，而是每次破坏性动作都能绑定同一个进程实例、人类确认能绑定可复核证据、发布入口能稳定执行到当前实现。按照这个标准，当前仍存在两个 P1 缺口和若干 P2 风险。

### 实际全局安装：明显落后且未经本轮验收

当前仓库源码与全局安装存在严重漂移：

| 项目                 | 仓库源码 | 全局安装 |
| -------------------- | -------: | -------: |
| skill 版本           |  `1.4.1` |  `1.3.0` |
| `SKILL.md` 字符数    |   18,194 |   10,601 |
| PowerShell 文件数    |        9 |        1 |
| PowerShell 总行数    | 约 2,026 |      806 |
| 模块化 `scripts/lib` |       有 |       无 |
| 全局目录链接到源码   |   不适用 |       否 |

这不是单纯的文档版本号问题。用户在 AI 工具中触发全局 skill 时，实际可能执行旧的单文件实现，而不是仓库中已经审计过的 `1.4.1`。因此，即使仓库源码测试全部通过，也不能证明用户当前入口已经获得相同保护；现有证据证明的是“旧版、缺少本轮加固、未经本轮验收”，并不能单独证明 `1.3.0` 整体不健壮。

从用户体验看，这也是最危险的“隐晦风险”：维护者看到仓库已经加固，会误以为问题已经解决；用户却继续运行旧版本，故障体感不会变化。

## Token 与运行成本

### 脚本运行时间不高

本次会话前段多次 live dry-run 的执行时间约为 2.8 至 3.8 秒；最终主代理在本地解析、只摘要回传的重跑为 4.268 秒。在 190 至 196 个目标进程的观测规模下，`CandidateCount` 均为 `0`。就 Windows 进程、CIM、端口和父子拓扑观察而言，这个时间成本可以接受，当前没有证据支持为了运行性能换语言。

### 模型读取成本很高

成本的主要来源是输出协议，而不是 PowerShell 本身。

| 内容                            |                                                         实测或估算 |
| ------------------------------- | -----------------------------------------------------------------: |
| 源码 description                |                                      657 字符，启发式约 233 tokens |
| 完整源码 `SKILL.md`             | 18,194 字符，约 4,549 tokens 下界；中英文混合启发式约 8,294 tokens |
| 单次默认 live dry-run           |                                         约 672,000 至 747,000 字符 |
| 单次默认 dry-run token 保守下界 |                       按字符数除以 4，约 170,000 至 187,000 tokens |
| 同一 JSON 压缩后的字符数        |                              约从 692,000 降至 249,000，减少约 64% |
| 只保留决策摘要                  |                                                        约 701 字符 |

默认输出会把大量 `Processes` 明细、命令行、工作目录、重复的安全说明和 WorkBuddy 状态交给模型。即使模型上下文能够容纳，仍会带来四种成本：API token 费用增加、重要候选被淹没、模型漏读概率上升、机器级进程和路径信息暴露面扩大。

压缩 JSON 只能缓解字符浪费，不能解决“默认输出了不需要的数据”这一根因。真正高 ROI 的做法是把默认 stdout 改为决策摘要，只返回候选、阻断原因、WorkBuddy 分组、验证状态和下一步；完整进程明细必须通过显式参数开启，或者写入受控临时文件后由工具按需查询。

### `SKILL.md` 本身不是最大成本

`SKILL.md` 约 18,000 字符，确实偏长，但其成本比单次 full dry-run 小一个数量级以上。继续过度压缩 description 或删除关键规则，节省有限，却会重新制造发现性和安全说明缺失。description 应保持只描述触发条件；正文可以通过 reference 渐进披露，但不能为了缩短 token 静默删除历史约束。

因此，token 优化的第一刀应砍输出，不应先砍知识。

## 隐晦风险清单

### P1：未发布源码没有到达用户入口

三份插件 manifest 当前均为 `8.3.6`，但 `CHANGELOG.md` 对本技能只记录到 `1.3.0`，没有 `1.4.0` 或 `1.4.1` 的发布记录；`8.3.6` 条目还写着“技能树本身无内容变更”。当前 `1.4.1` 加固仍属于工作区源码，不能把这种状态称为 manifest 与技能版本冲突；准确问题是本轮源码尚未形成发布记录、安装产物和全局同步证据。

风险不只是“忘写日志”，而是缺少一条可证明的链路：源码版本变更、发布说明、插件产物、安装 smoke test、全局同步。任何一环缺失，维护者都无法回答“用户现在执行的到底是哪一版”。

### P1：通用 `-Force` 重试存在 PID 复用窗口

普通清理路径在第一次 `Stop-Process` 前会核验进程身份；等待约 300ms 后，如果同一 PID 仍存在，`-Force` 重试只检查 PID 是否存在，没有再次核验 `Name + CreationTime`。

Windows 可能在原进程退出后复用 PID。虽然 300ms 窗口较短，但这是破坏性工具，不应把“小概率”当成安全证明。修复方式是强制重试前再次调用实时身份核验；不匹配时记录 `skipped-pid-reused-before-force`，并增加首次停止后 PID 被复用的回归测试。

### P1：WorkBuddy 双确认没有绑定 dry-run 证据

`ConfirmWorkBuddyPoolNotCurrent` 和 `ConfirmWorkBuddyPoolIdle` 当前是两个裸布尔声明。它们不能绕过已识别的当前祖先链、监听端口、年龄和置信度保护，但调用者如果错误声称“非当前且空闲”，仍可能停止一个没有被当前脚本识别为活跃、实际上仍在工作的池。

更稳健的设计应把 Apply 确认绑定到前一次 dry-run 的短期指纹，例如池 PID、各进程 CreationTime、拓扑 PID 集合、采样时间和随机确认令牌。Apply 时必须重新计算并匹配；裸布尔参数不能单独构成破坏性授权。

### P2：命令行脱敏覆盖不完整

当前脱敏主要覆盖 `--token`、`--access-token`、`--api-key` 和 `--authorization`，未系统覆盖 `Bearer`、`TOKEN=value`、`--password`、`--secret`、`--auth-token`、URI userinfo 等常见凭据形态。

默认 full JSON 和 Apply 台账都可能携带命令行、可执行路径和工作目录提示。即使台账只允许写入系统临时目录，也可能被日志采集器、后续 agent 或诊断工具读取。应扩展脱敏键名和值形态，并用专门 fixture 覆盖环境变量赋值、Authorization 头和带凭据 URI。

### P2：普通模式无法发现新 PID respawn

普通模式验证只检查原候选 PID 是否仍存在，然后固定返回空的 `RespawnedProcessPids`。如果父服务用新 PID 拉起 Node 或 `cmd.exe`，台账可能给出比真实状态更乐观的结果。

建议在停止后重新采样，只报告与原命令指纹、父服务或任务范围匹配的新 PID；与 WorkBuddy 一样，不得在同一轮自动追杀新进程。

### P2：长函数接近结构门禁

模块化已经解决了“1700 行单文件”的主要维护问题，但 `Invoke-AgentTeamNodeCleanup` 约 274 行，距离 280 行门禁只剩很小余量；`New-CleanupAuditEntries` 和 `Build-WorkBuddyGrouping` 也都超过 250 行。

这会诱使后续 AI 为增加一个安全分支而突破门禁，或者在 ledger、执行、验证三条路径之间漏同步字段。下一轮可以进行函数级拆分，但应在输出协议和 P1 风险修复之后，不需要再次进行大规模文件拆分。

### P2：全量审计输出扩大隐私和误判面

全量 JSON 不只是 token 问题。它包含本机进程、命令行、路径、父子关系和端口信息。模型可能因为上下文过长而忽略真正的阻断项，也可能把未命中的普通 Node 服务误解为 agent team 残留。

应把“机器观测数据”和“模型决策输入”分离：脚本可以在本地完整观察，但默认只把经过脱敏、聚合和风险筛选的摘要交给模型。

## 是否需要换语言

不建议换语言。

PowerShell 对 Windows CIM、进程树、`Stop-Process`、临时目录和 `ShouldProcess` 有原生支持，技能安装后不需要额外运行时。改成 TypeScript 会引入 Node 运行时和包依赖，而该技能的目标恰好是清理 Node 进程；这会增加启动进程、依赖解析、分发兼容和“清理器自身是否被误判”的新问题。

当前主要缺陷都不是 PowerShell 无法解决：输出摘要、身份复核、确认令牌、脱敏、respawn 观察和发布同步都可以在现有实现内完成。换语言会扩大改动面，却不会自动改善安全语义。

## 建议的下一轮优化

我建议继续优化，并采用一个受控的 A 方案，而不是重写：

1. <!-- TODO: 可接受的优化 --> **先降低默认输出成本。** 默认 stdout 只返回摘要；增加显式完整审计开关。摘要至少包含 `Mode`、`CandidateCount`、候选 PID、阻断原因聚合、WorkBuddy 分组、停止结果、验证结果和是否存在 respawn。
2. **再闭合发布与安装链路。** 补齐本技能 `1.4.0/1.4.1` 的变更记录，按仓库发布流程生成可验证产物，再通过正式同步刷新全局安装；增加源码与安装包版本、文件清单和哈希的一致性检查。
3. **修复 `-Force` 身份复核。** 在强制重试前重新验证 `PID + Name + CreationTime`，并补 PID 复用回归测试。
4. <!-- TODO: 可接受的优化 --> **把 WorkBuddy 确认绑定 dry-run 指纹。** Apply 不再只信两个布尔参数；引入短期审计令牌或受控 dry-run ledger 输入。
5. **扩展凭据脱敏。** 覆盖参数、环境赋值、Bearer 和 URI 凭据，并明确路径字段的默认披露策略。
6. **增加普通模式 respawn 报告。** 重新采样并报告新 PID，但保持“不在同一轮追杀”的安全边界。
7. **最后拆分长函数。** 优先拆参数门禁、观察上下文、候选决策、执行和验证收口，不增加新语言或额外框架。

建议把前四项视为下一轮必须完成的高 ROI 工作；后面三项可以在同一轮按风险和工期决定是否纳入。

## 不建议的方向

不建议继续通过压缩 description 来节省成本。description 当前约 657 字符，不是主要 token 来源，过度删改会降低技能触发准确度。

不建议默认生成 `agent-process-ledger.dry-run.json` 或其他工作区报告。默认 dry-run 应保持 stdout-only；只有显式请求完整审计文件时才允许写入，而且 Apply 台账仍应限定系统临时目录。

不建议把 full dry-run JSON 原样交给主模型后再让模型总结。摘要应由确定性脚本生成，不能依赖具体 AI 模型“帮忙清理垃圾文件”或“帮忙删除报告”。

不建议现在继续横向拆成更多 PowerShell 文件。当前 8 个 lib 模块已经足够表达职责，优先降低单个函数复杂度即可。

## 决策建议

如果现在停止优化，技能的仓库源码仍可用于谨慎的人工 dry-run，但不能对用户宣称“全局入口已经健壮”，也不能忽略每次十几万 token 的默认读取成本。

如果继续优化并完成上述前四项，预期可以同时获得三类直接收益：用户真正执行到新版安全门禁；默认审计输入从十几万 token 降到几百或几千 token；破坏性停止进一步绑定进程实例和可复核证据。

因此我的建议是：**继续优化，但严格限定为输出协议、分发闭环和 P1 安全门禁，不换语言，不再做无边界架构升级。**

## 当前可确认与仍待验证的边界

当前可确认：仓库源码为 `1.4.1`，全局安装为 `1.3.0`；全局安装不是指向源码的链接；最终 stdout-only dry-run 在 4.268 秒内审计 190 个目标进程、候选数为 0，且工作区 `agent-process-ledger.dry-run.json` 数量在运行前后均为 0；仓库模块化实现已经显著降低单文件维护成本；当前工作区源码尚未形成对应的发布记录和全局安装证据。独立复核代理曾受 CIM 权限限制，最终主运行没有向模型回传原始全量 JSON，因此 live 输出规模仍未再次精确验证。

仍待下一轮实现后验证：摘要输出能否覆盖所有决策必要字段；发布后的真实全局安装是否与源码一致；PID 复用测试能否阻断 Force 重试；WorkBuddy 指纹是否能在防误杀与操作便利之间保持合理平衡。
