# 2026-08-31 双 Qoder 会话并行重载导致 CPU 饱和的排查报告

> **报告所使用的 agent 工具说明**：本报告由 Qoder（桌面 agent 会话）完成。
> **报告所使用的 AI 模型说明**：Qoder 内置模型完成（Qoder 不对外披露具体模型标识）。

## 一、背景

2026-08-31，同一台机器上同时运行两个 Qoder 会话：

- **会话 A（本报告作者）**：执行任务 082——升级 `install-mcp` 技能，随后进入 `release-ai-plugins` 发布准备。
- **会话 B（用户保留，继续推进）**：执行任务 084——升级 `install-skills` 与 `sync-local-global-agents-skills`，包括 vitest 测试、prettier 格式化、tsx 同步脚本，以及 118 个 skills 的目录级链接重建。

发布准备阶段，会话 A 发现工作区被会话 B 的在途改动污染（`skill-registry.json` 与技能树不一致），经用户拍板选择「等 084 完成后合并发布」。会话 A 随即使用 `wait_chat_sessions` 对会话 B 做内联等待，期间用户发现整机 CPU 被打满、系统明显卡顿。

## 二、时间线

1. 会话 A 完成 install-mcp 技能内容升级与验证。
2. 会话 A 启动发布流程，`registry --check` 暴露出会话 B 的未提交改动，确认并行冲突。
3. 用户选择「等 084 完成后合并发布」；会话 A 开始 `wait_chat_sessions` 阻塞等待（每次上限 60 秒），等待间隙插入 `git status` / `git log` 检查。
4. 用户发现 CPU 饱和并中断会话 A。
5. 会话 A 立即停止一切轮询与命令，进入静默；用户选择让会话 B 自然跑完。

## 四、归因：CPU 到底被谁吃完

**结论：CPU 不是被「监听另一个会话」这个动作吃掉的，而是「两个会话并行重载干活」叠加机器既有负载。** 分三层：

1. **两个会话的工具链并行运行（主因）**：会话 B 正在跑 vitest 全量测试、tsx、prettier、118 个 skills 的目录级链接替换（海量文件系统操作）；会话 A 前期也运行了 prettier、Node registry 生成器、git、memorix CLI。node 进程数在事故时达到 16 个，会话 A 静默后降至 7 个——这 9 个进程的差值就是会话 A 侧工具链的直接证据。
2. **Qoder（Electron）宿主进程**：榜首 `Code`（PID 19480）事故时已累计 8490 秒 CPU；会话 A 静默后该进程仍新增约 2752 秒——这部分增量属于用户选择保留、仍在推进 084 的会话 B，不是会话 A 的残留。
3. **与 agent 无关的机器背景负载**：360ChromeX、QQ、msedgewebview2 等，合计也占用相当份额。

## 五、等待机制澄清：是不是「监听」吃掉了 CPU

- `wait_chat_sessions` 是**事件驱动的阻塞等待**，单次调用上限 60 秒，等待期间不存在本地 busy loop，CPU 开销接近零。
- 但它会**保持当前 turn 与会话运行态存活**：渲染进程、扩展宿主、MCP 连接、上下文都维持在活跃状态。会话 A 的错误不在「等待这个调用贵」，而在**选择了内联等待而不是静默交接**，让自己一直挂在战场上，与重载的会话 B 并行挤占机器。
- 关于「是否设计缺陷」：等待机制本身没有问题；真正的缺口是**并行会话之间没有负载感知与错峰协调**——两个会话各自调度重载命令时，没有任何一方会先看机器余量。这是本次事故要沉淀的编排约束，也是值得反馈给 Qoder 产品侧的改进点。

## 六、会话 A 认账的编排失误

1. 发现并行会话后，第一选择是「保持 turn 内联等待」，而不是「立即静默、把恢复权交还用户」——放大了并行窗口。
2. 等待间隙还插入 `git status` / `git log` 检查，属于不必要的唤醒与 I/O。
3. 在决定「等」之前，没有先向用户预警双会话重载并行的机器风险；CPU 过载由用户亲自发现，属于监控缺位。

## 七、已执行的处置

1. 停止所有 `wait_chat_sessions` 轮询与 git 检查，会话 A 完全静默。
2. 发布流程挂起，改为用户触发式交接：084 完成后用户说「发布」，再一次性合并发布。
3. 未杀会话 B 的任何进程：其正处于 `~/.qoder/skills` 目录级链接替换关键步骤，强杀会留下半替换状态。

## 八、后续约束

1. 需要等待另一个会话的产物时，默认「结束当前 turn，交给用户触发」；禁止保持 turn 做内联阻塞等待。
2. 并行调度重载命令（测试、构建、registry 生成、批量文件操作）前，先确认机器是否已有其他重载会话；必要时先错峰并向用户说明。
3. CPU 饱和窗口内不再发起任何命令；取证仅限一次性轻量采样。
4. 发现另一会话正在执行批量文件系统变更时，不杀其进程；强杀会留下半完成目录状态。
5. 归因必须事实驱动：等待机制接近零开销，吃 CPU 的是并行工具链——不赖 busy loop，也不甩锅环境。
