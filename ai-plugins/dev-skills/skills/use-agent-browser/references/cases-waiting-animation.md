# 案例集：等待、动画与 headless

> use-agent-browser 技能参考层。案例均来自真实项目实战复盘（已脱敏）。共同背景：被测页面包含 JS 驱动动画（GSAP、Three.js WebGL、ECharts 循环动画）时，「等多久」「能不能冻结」「能不能无头」都有硬边界。命令语法以 `agent-browser skills get core` 为最终权威。

## 案例 1：headless + 无限动画 = CPU 死亡螺旋

- **现象**：无头浏览器跑视觉测试，CPU 100%，机器卡死；用户当场要求永久弃用该方案。
- **根因**：像素级截图对比内置「多帧像素稳定」循环，会反复重渲染等待画面稳定；而 GSAP 呼吸动效、ECharts 轮播、Three.js WebGL 渲染循环不受 VSync 限制，无头模式以最高帧率运行——两者叠加形成死循环。
- **关键误导点**：以为 `reducedMotion: 'reduce'` 能冻结所有动画——它只能冻结 CSS 动画，对 JS 驱动的动画无效。
- **有效修复**：动画密集页面强制可见浏览器（headed），即使 CI 也不例外；整条无头像素对比方案被弃用，改为「可见浏览器 + 目标元素视口截图 + 人工判读」。
- **验证方式**：可见浏览器下 CPU 占用正常，验收闭环完成。
- **后续约束**：包含无限动画的页面禁止无头模式与自动像素对比；视觉验收先 smoke 再矩阵，首轮禁止大而全脚本。

## 案例 2：强行干预动画无效且有害

- **现象**：为了让入场动画「立刻结束」再截图，尝试 `gsap.globalTimeline.progress(1)` 与手动覆盖 `element.style.opacity = '1'`，均失败。
- **根因**：独立 timeline 不受 globalTimeline 影响；GSAP 在下一 tick 会重新覆盖被手动修改的内联样式。
- **关键误导点**：早期设计文档里甚至写过「手动置 opacity=1 复位入场动画」的脚本——后来被实测证伪并以新教训覆盖。
- **有效修复**：等待动画自然完成（入场动画 2-3s 量级）；确需停帧时用 `gsap.globalTimeline.pause()` + `gsap.ticker.sleep()` 冻结时间轴。
- **验证方式**：自然完成后截取的画面稳定，连续截图不再变化。
- **后续约束**：不要用脚本「骗过」动画系统；判定稳定用 DOM 数值轮询（见案例 4），不靠截图时机猜。

## 案例 3：loadEventFired 对动画大屏不可靠

- **现象**：页面 `load` 事件已触发，但关键面板与 3D 区域仍未渲染完成； fullscreen 验证脚本因未处理窗口状态报「最小化窗口需先还原」错误。
- **根因**：`load` 只代表资源加载完成，不代表动画/异步渲染收敛；窗口状态问题则是 fullscreen 的前置条件。
- **关键误导点**：把「load 完成」当成「可以截图/度量了」的充分条件。
- **有效修复**：固定视口后等待 8-9 秒再读 DOM 几何；用 `eval` 轮询关键数值序列直到连续两次一致；fullscreen 前先处理窗口状态并单独归档。
- **验证方式**：固定视口 + 数值轮询后，DOM 几何（canvas/map 占比）度量稳定，8 项度量全部通过且 console issue 为 0。
- **后续约束**：动画页的「可以验收」信号是「数值轮询收敛」，不是任何单次事件。

## 案例 4：等待策略表

| 场景         | 等待量级    | 等什么                                                    |
| :----------- | :---------- | :-------------------------------------------------------- |
| 首屏首次加载 | ≥8s         | loading 遮罩消失（3-4s）+ GSAP 入场动画（2-3s）+ 渲染稳定 |
| SPA 路由切换 | ≥5s         | 仅入场动画                                                |
| 刷新当前页   | ≥6s         | 缓存复用下的动画重放                                      |
| 普通静态页   | networkidle | 无动画时即可                                              |

- **现象/根因**：三类场景统一用一个等待时长，要么等不足产生假故障，要么过量等待浪费时间。
- **有效修复**：按场景分档等待 + `eval` 数值轮询兜底；轮询模板见 `command-cookbook.md` 第 5 节。
- **关键误导点**：用单一等待时长套所有场景——要么等不足产生假故障，要么过量等待浪费时间。
- **验证方式**：按分档等待 + 数值轮询后，三类场景的截图与 DOM 度量均稳定收敛。
- **后续约束**：等待量级来自本项目实测，移植到其他页面时先用 smoke 校准，不直接照抄数字。

## 案例 5：SSR 页面 eval 的时机与「无错不水合」诊断链

- **现象**：SSR 文档站上 `eval` 取不到客户端注入的 CSS 变量；另一场景整站交互全死、console 干净。
- **根因**：客户端变量在水合完成后才存在；模块脚本执行失败不一定走 `console.error`。
- **关键误导点**：把「eval 返回空」当成「变量不存在」，把「console 干净」当成「前端无错」。
- **有效修复**：eval 前确保水合完成（交互触发或等待）；无错不水合时按诊断链执行：`!!document.querySelector('#__nuxt').__vue_app__` 判定挂载 → 动态 `import(entrySrc + '?v=diag')` 抓真实 SyntaxError → CDP `initiator.url` 定位导入方。
- **验证方式**：诊断链定位到了真实崩溃模块及其导入方，修复后水合恢复。
- **后续约束**：SSR 站验收的 eval 一律安排在交互之后；「无错」必须结合水合判定一起解读。

## 案例 6：WebGL 在 headless 下的两类假象

- **现象**：headless 环境截图中 3D 地图区域全黑；直接读取 WebGL canvas 像素得到全透明。
- **根因**：headless Chrome 中 WebGL 可能未成功初始化（环境限制）；`readPixels` 的采样网格可能错过不透明像素。
- **关键误导点**：把环境限制当成视觉回归，或把透明读数当成「页面空白」。
- **有效修复**：3D 区域判定使用可见浏览器 + 截图像素采样；`readPixels` 不作为非空断言。
- **验证方式**：可见浏览器下同一区域渲染正常，确证 headless 黑屏属环境限制。
- **后续约束**：WebGL/canvas 内容的「空白」结论必须在可见浏览器中复核后才能成立。
