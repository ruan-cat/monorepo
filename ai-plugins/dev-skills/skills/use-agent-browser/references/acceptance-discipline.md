# 验收纪律：会话分层、止损与证据门禁

> 本文是 use-agent-browser 技能的参考层：把「一次验收」拆成可停止的分层结构，并规定失败时的止损动作、常见自我欺骗与提交前的证据门禁。命令语法以 `agent-browser skills get core` 的当前版本输出为最终权威。

## 1. 会话分层：四层 checkpoint，不把一次长跑当成验收

一次环境验收使用一个具名 headed session，但内部拆成四层 checkpoint。层与层之间只保存结构化状态，不通过「再开一个 session」补洞。

|      checkpoint       | 目标                                                          | 允许的动作                         |           失败状态            |
| :-------------------: | :------------------------------------------------------------ | :--------------------------------- | :---------------------------: |
| A 能力探针（≤5 分钟） | headed launch、前台 visibility、截图、network、close 是否可用 | 只访问目标 URL，禁止业务操作       |      `blocked`，不进入 B      |
|    A2 reload 探针     | 仅在 C 需要 reload 时验证单次受控 reload 与原 session 恢复    | 同一 session 单次受控 route/reload |  失败只阻塞 C 的 reload 子项  |
|    B 产品核心矩阵     | 目标页面的核心用户路径与稳定状态                              | 真实点击/键盘/滚动；稳定状态截图   |    产品证据 `pass/partial`    |
|    C 故障/资源补证    | 首载/刷新失败、single-flight、水合、artifact/资源状态         | 优先不 reload 的 route/fetch 控制  | `pass/blocked/not-applicable` |
|      D 独立复核       | 复核任务源、工件、文件、尺寸、SHA、日志与状态映射             | 只读，不重新开浏览器               |      `pass/needs_check`       |

### 1.1 分层边界

- 建议时间盒：A 5 分钟、B 20–30 分钟、C 10 分钟、D 5 分钟；A2 只允许一次并计入 C 的时间盒。超过时间盒先停下记录，而不是继续试错。
- 一个环境的一次验收只服务一个范围；旁路页面（普通文档页、其他路由）只能作为独立 checkpoint，不得塞进核心矩阵。
- A 的 session 注册不等于 B 的业务通过；B 的截图不能替代 C 的失败恢复；D 的复核不能把缺失材料改写成通过。
- 证据状态只允许 `pass`、`partial`、`blocked`、`not-run`。`blocked` 表示工具/外部权限事实，既不表示产品成功，也不表示产品失败。
- 矩阵未完成、证据未登记前不得 `close`，也不得用新 session 接着补齐并宣称「同一次通过」。

## 2. 失败边界与止损

| 症状                         | 立即动作                                                                                  | 禁止做法                         |
| :--------------------------- | :---------------------------------------------------------------------------------------- | :------------------------------- |
| `tab_gone`                   | 在原 session 查看 `tab list`，用 `tab new <url>` 重新绑定同 URL，重跑 snapshot 与基线检查 | 新建第二 session 拼接            |
| `EOF` / `connection refused` | 先查 daemon、Chrome PID、CDP 端口；同一 Chrome 可达时只重连原 session，最多一次           | 盲目重复 launch/open             |
| `DevToolsActivePort` exit 3  | 保留原始日志；未成功启动时只做一次同方式恢复；已有 session 丢失则直接 `blocked`           | 连续启动多个 Chrome              |
| `captureScreenshot` timeout  | 停止同命令重试；稳定后改用更小区域/关键状态截图，或标记截图缺失                           | 删掉 timeout、拿旧截图冒充 fresh |
| reload 后控制面丢失          | 保留已完成的 B 证据，C 标记 `blocked`，结束该环境                                         | 为补失败图重启/换 session        |
| 页面产品断言失败             | 保留截图、DOM、网络与 console，停止该环境矩阵                                             | 继续操作到「看起来差不多」       |
| 服务器或浏览器进程异常       | 记录 PID/端口/日志，先结束当前环境                                                        | 静默换环境或换 session           |

恢复仍失败时，当前环境是 `blocked` 或 `needs_check`，不是「通过」。控制面 `blocked` 不得改写为产品 `fail` 或 `pass`；任务勾选只能发生在证据完整之后。

## 3. 常见合理化借口

| 借口                                 | 纠偏                                                         |
| :----------------------------------- | :----------------------------------------------------------- |
| 「只差一个场景，另开 session 更快」  | 破坏单 session 可回放性；回到原 session 或记录未完成         |
| 「顺便测一下旁路页面更全面」         | 范围不是越大越好；只有任务源明确要求才另开 checkpoint        |
| 「DOM 已经通过，截图可以省略」       | 视觉任务需要可见证据；缺截图只能是参考/未完成                |
| 「EOF 多试几次总会好」               | 先查控制面与端口；无界重试只制造假进展                       |
| 「构建通过所以浏览器肯定没问题」     | build 只证明构建链，不证明真实交互、滚动、主题或焦点         |
| 「旧截图内容一样，拿来补今天的记录」 | 没有同 session、同 viewport、同提交与哈希链就不是 fresh 证据 |

## 4. Red Flags — STOP

出现任一项，停止并回到「先锁定范围」：**自报完成只是 candidate，证据链才是交付。**

- 同一环境出现第二个 session 名称。
- 没读基线就截图。
- 截图失败后没有保留原始日志。
- 用 DOM、build、HTTP 200 或局部截图勾选完整任务。
- 把旁路页面、其他路由或其他环境混入当前核心矩阵。
- 未完成证据登记就关闭浏览器或启动替代浏览器。
- 能力探针超过 5 分钟仍未通过，或同类控制面故障已发生第二次。
- 为了补一张孤立截图而 reload、换 profile、换端口或开第二个 session。

## 5. 提交前证据落盘校验

在勾选任务或提交验收工件前，逐行扫描证据清单里的截图引用，并同时确认：

1. 路径存在、文件仍位于当前任务的 evidence 目录，图片尺寸与登记的 viewport 一致。
2. 现场重新计算哈希（如 `Get-FileHash -Algorithm SHA256`）与清单登记值完全相同；任一缺失或不匹配都标记为 `needs_check`，不得用旧图、同名图或早期 session 补齐。
3. 每条截图能回指当前环境、当前 session 和具体场景；只完成 DOM/网络断言但没有截图落盘时，必须记录为「部分」，不能写成「通过」。

建议用一次性只读脚本输出 `checked / missing / mismatched` 汇总，再人工抽查；不要在发现断链后重新开 session 只为制造一张孤立截图。
