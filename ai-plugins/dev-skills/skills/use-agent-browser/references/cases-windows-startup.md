# 案例集：Windows 启动与连接

> use-agent-browser 技能参考层。案例均来自真实项目实战复盘（已脱敏），按「现象 → 根因 → 关键误导点 → 有效修复 → 验证方式 → 后续约束」结构沉淀。命令语法以 `agent-browser skills get core` 为最终权威。

## 案例 1：Chrome 自动启动 exit code 3

- **现象**：Windows 下 agent-browser 自动启动 Chrome 失败，报 exit code 3（伴随无 DevToolsActivePort）；两个不同项目先后复现。
- **根因**：新版 Chrome 默认启动方式与自动化环境不兼容（沙箱/启动参数缺失），不是站点故障。
- **关键误导点**：把「工具启动失败」误判为「被测站点故障」——曾据此得出整站路由渲染错误的错误结论并撤回报告。
- **有效修复**：为会话追加 `--args "--no-sandbox"` 后启动成功。
- **验证方式**：追加参数后 `open` + `get title` 正常返回；页面加载、截图、DOM 检查全部可用。
- **后续约束**：把启动参数固化进 smoke 脚本；启动失败先区分「工具失败」与「站点失败」，工具失败不得写入站点结论。

## 案例 2：doctor 失败被误读为会话不可用（分离诊断模型）

- **现象**：`doctor` Launch test 失败、daemon EOF、typed MCP `open` 无响应同时出现；同时默认会话的 `screenshot` 却能成功保存页面。
- **根因**：`doctor` / 新建链路失败只能证明**新建或接管链路异常**，不能证明**现存会话**不可读。
- **关键误导点**：把三类失败信号打包当成「浏览器全挂」，差点把「现存会话可正常读取 DOM 并截图」的事实丢掉，转而怀疑 SSR 渲染。
- **有效修复**：分离诊断——先对现存会话跑最小探针（`get url`、元素计数、`scrollintoview`、`screenshot`）；探针通过就继续用现存会话完成任务，只有现存会话也不响应时才处理 daemon/CDP 启动问题。
- **验证方式**：探针返回的截图经实际查看为真实页面内容；后续对该会话的枚举、滚动、截图操作全部成功。
- **后续约束**：daemon EOF 后子命令偶然成功不算可靠流程，不得作为标准路径记录；EOF 处置顺序为 `doctor` → `close` → 重启会话。

## 案例 3：CDP 接管本机 Chrome

- **现象**：用户要求使用本机 Chrome 而非 agent-browser 自带浏览器，且需要可见窗口做视觉验收。
- **根因**：默认启动器无法同时满足「来源可证明 + 可见窗口 + 不碰用户日常 profile」。
- **关键误导点**：在默认启动器反复失败后才临时改用接管路径，没有把它固化为首选。
- **有效修复**：显式启动本机 Chrome（独立临时 profile + `--remote-debugging-port=<port>`），再 `agent-browser --cdp <port>` 接管。实测接管后可枚举页面图片、滚动目标元素、保存视口截图。
- **验证方式**：接管会话内完成目标图视口截图并人工判读；临时 profile 与端口在任务结束后登记并清理。
- **后续约束**：Windows 本地视觉验收首选此路径而非失败后临时补救；接管实例必须登记端口、`user-data-dir`、PID 与关闭策略。

## 案例 4：headless=new 降级连接

- **现象**：自动启动 Chrome 反复 exit 3，需要一条不依赖默认启动器的链路。
- **根因**：默认启动链路在该机器环境不可用，但 Chrome 本体可用。
- **关键误导点**：同一方法原地重试 8 次以上才换方案——重试纪律（失败 ≥2 次换本质不同方案）执行得太晚。
- **有效修复**：手动 `chrome --headless=new --remote-debugging-port=<port>` 启动 + `agent-browser connect <port>`。
- **验证方式**：连接后页面加载与截图正常。
- **后续约束**：headless 仅作降级手段；动画密集页面禁止 headless（见 `cases-waiting-animation.md` 案例 1）；降级链全步骤记录证据。

## 案例 5：Chrome 连接器模式 "Browser is not available"

- **现象**：用户要求使用自己的 Chrome（扩展 + Native Messaging 连接器模式）；诊断显示 Chrome 已安装、扩展已启用、manifest 正确，但连接器返回 "Browser is not available"。
- **根因**：Chrome 当前未运行，连接器无法建立绑定——是状态问题，不是配置问题。
- **关键误导点**：配置三件套全部正常，容易误判为「还需要改配置」。
- **有效修复**：等待用户打开 Chrome 或明确授权启动；期间关闭 agent-browser 独立会话与本地 dev 进程，避免资源堆积。
- **验证方式**：用户打开 Chrome 后连接器建立绑定。
- **后续约束**：不得擅自启动用户浏览器；连接器模式下验收对象是用户 Chrome，独立会话不应并行残留。

## 案例 6：typed MCP open 长时间无响应

- **现象**：MCP 工具形态 `agent_browser_open` 对本地 VitePress 与 Nuxt 页面均等待 300 秒超时；另一场景 headed/headless 启动均挂起约 60 秒后被终止。
- **根因**：自动化环境下的启动/等待链路异常，多框架复现说明与被测框架无关。
- **关键误导点**：反复等待或重试，期望「这次会好」；后续偶然成功掩盖了链路不可靠。
- **有效修复**：记录失败路径后立即切换证据来源（Chrome DevTools 类工具完成本轮验收），在 findings 中保留失败记录；不再重复等待。
- **验证方式**：切换后验收完成且失败路径有记录，后续会话不会被误导重试。
- **后续约束**：单次等待超过合理阈值（分钟级）即切换证据来源；「该轮验收以 X 证据为准」的决策必须写入工件。

## 案例 7：浏览器实例可用性预检

- **现象**：依赖某个浏览器插件/实例执行验收时，实例列表返回空（如 `agent.browsers.list()` 为空列表），任务中途才发现不可用，被迫临时切换方案。
- **根因**：自动化环境中的浏览器实例是否就绪是运行时状态，不是配置的必然结果。
- **关键误导点**：默认「浏览器一定可用」直接开写验收脚本，不先确认实例存在。
- **有效修复**：依赖浏览器实例前先做可用性预检（`agent-browser doctor`、实例/会话列表、最小探针）；不可用时改用等价工具完成本轮验收，并显式记录环境限制。
- **验证方式**：替代路径完成验收且「插件不可用」的限制被写入工件，后续会话不再盲目依赖。
- **后续约束**：把可用性预检纳入 smoke 第一步；「改用替代工具」的决策与原因必须记录（对齐案例 6 的切换纪律）。
