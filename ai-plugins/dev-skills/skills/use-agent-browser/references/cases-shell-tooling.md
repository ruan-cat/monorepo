# 案例集：Shell、eval 与命令写法

> use-agent-browser 技能参考层。案例均来自真实项目实战复盘（已脱敏）。共同主题：**驱动 agent-browser 的 shell 层写法错误，会制造假故障甚至污染工作区**。命令语法以 `agent-browser skills get core` 为最终权威。

## 案例 1：PowerShell 复杂 inline eval 生成 0 字节脏文件

- **现象**：把包含 `||`、箭头函数、对象字面量的 eval 脚本和多命令串接塞进 PowerShell 命令行后，eval 失败，且仓库根出现 3 个 0 字节未追踪文件（形如 `!img.complete`、`({i`、`img.naturalWidth` 的文件名）。
- **根因**：PowerShell 对特殊运算符和引号的拆解与 bash 不同，重定向被错误解析成了文件创建。
- **关键误导点**：把 Bash heredoc 示例生搬硬套进 PowerShell；失败后只盯着 eval 报错，没先查工作区。
- **有效修复**：用精确 `LiteralPath` 删除本次产生的文件；复杂脚本改走 CLI 支持的 stdin/base64 传参入口，或拆成 `get count`、`get attr` 等简单命令；每次 eval 后运行 `git status` 复查。
- **验证方式**：`git status` 确认无残留脏文件，未纳入任何提交。
- **后续约束**：PowerShell 中禁止复杂 inline eval；「eval 失败」的第一反应是查工作区是否被污染。

## 案例 2：元素引用需要引号包裹

- **现象**：在 PowerShell 中点击 `@e15` 时行为异常，加引号写成 `'@e15'` 后点击成功。
- **根因**：`@` 在 PowerShell 中有特殊语义（数组/哈希字面量），裸写引用可能被拆解。
- **关键误导点**：把 CLI 示例里的裸引用直接粘进 PowerShell。
- **有效修复**：`@eN` 引用在 PowerShell 中一律用引号包裹。
- **验证方式**：加引号后交互生效（按钮状态变化可观察）。
- **后续约束**：跨 shell 使用时，引用与含特殊字符的参数一律加引号。

## 案例 3：包管理器参数透传污染验收结论

- **现象**：`pnpm --filter <pkg> dev -- --port 3100` 启动的文档站全路由渲染异常，浏览器快照「证实」了这一点，报告据此给出整站错误结论后撤回。
- **根因**：多余的 `--` 被透传给了被测程序（实际执行 `nuxt dev "--" "--port" "3100"`），dev server 状态本身是坏的。
- **关键误导点**：浏览器证据是真实的——但它在验收一个**启动错误的被测服务**；「快照看起来可信」掩盖了上游启动参数错误。
- **有效修复**：修正启动命令后重新验收；报告撤回并记录根因。
- **验证方式**：正确命令启动后同一路由快照正常。
- **后续约束**：浏览器验收前先确认被测服务以正确参数启动；验收结论要携带「被测服务如何启动」的记录。

## 案例 4：命令名细节：`set viewport` 与响应式隐藏

- **现象**：设置视口的写法被写成 `set-viewport` 无效；窄视口下 header 元素「不渲染」被当成缺陷。
- **根因**：正确命令是 `set viewport <w> <h>`（空格分隔，非连字符）；header 容器是 `hidden md:flex` 类响应式布局，窄视口下本就不渲染。
- **关键误导点**：凭记忆猜命令名；没意识到被测样式本身是响应式的。
- **有效修复**：改用 `set viewport 1920 1080`，验收统一桌面视口。
- **验证方式**：桌面视口下元素正常渲染。
- **后续约束**：命令名不确定时先查 `agent-browser --help` 或 `skills get core`，不凭记忆写；验收视口先于结论确定。

## 案例 5：固定等待参数的写法时效

- **现象**：源材料中的 `wait --time 1000` 写法在当前 CLI 版本无效——实测不按参数等待，而是落到默认等待后超时报错；裸毫秒 `agent-browser wait 1000` 才是当前正确写法。
- **根因**：CLI 演进改变了参数形态；旧示例在文档/报告中留存后被转写。
- **关键误导点**：历史材料的命令写法被当成「永远正确」复制粘贴；且 CLI 对无效参数的报错信息（等待超时）与「参数不存在」相距甚远。
- **有效修复**：改用裸毫秒参数；把「以 `agent-browser skills get core` 当前输出为最终权威」固化为技能纪律。
- **验证方式**：实测 `wait 1000` 立即按预期完成，`wait --help` 与 core 内容中均无 `--time` 选项。
- **后续约束**：从任何历史材料复制命令前，先与当前版本 CLI 核对；core 内容随安装版本下发，这是它被设为权威的原因。

## 案例 6：启动参数未固化导致同类事故复发

- **现象**：同一台机器上，「Chrome 启动失败 → 临时加参数 → 恢复」的过程在多个项目重复发生；项目内无任何脚本固化该参数。
- **根因**：修复停留在「当次会话记忆」，没有落进 smoke 脚本或文档。
- **关键误导点**：认为「下次记得就行」。
- **有效修复**：把启动参数（如 `--args "--no-sandbox"`）、接管配方（CDP 端口 + 临时 profile）固化进项目 smoke 脚本或本技能配方（`command-cookbook.md` 第 4 节）。
- **验证方式**：后续会话直接按配方执行，不再重演失败-试错链。
- **后续约束**：踩过的环境坑必须落到「下次会话能直接执行」的载体，而不是留在人的记忆或聊天记录里。

## 案例 7：hash 路由与相对 base 的入口形态

- **现象**：以相对路径为 base 的静态部署应用（hash 路由），直接访问站点根路径得到 404/空页，据此截图差点误判整站异常。
- **根因**：hash 路由 + 相对 base 的应用必须以 `/index.html#/<路由>` 形态访问，根路径不是有效入口。
- **关键误导点**：把入口形态错误当成应用故障；用 404 根路径的截图作为「应用坏了」的结论证据。
- **有效修复**：按部署形态构造正确入口 URL（`/index.html#/目标路由`）后再进入验收流程。
- **验证方式**：正确入口下页面正常渲染，原结论撤回。
- **后续约束**：验收前先确认被测应用的路由模式（history/hash）与 base 形态；根路径截图不得作为应用故障的证据（与 URL 原样使用纪律配合：先原样打开，失败后按证据构造正确入口）。
