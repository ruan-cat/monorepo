# 决策边界：什么时候才该从 agent-browser 切到 Midscene（VLM 驱动）

> use-agent-browser 技能参考层。本文件只回答一个问题：**agent-browser 已经够用时，什么条件下才值得引入 VLM 驱动的 Midscene？**
> 结论先行：Midscene 是「视觉兜底通道」，不是「更聪明的 agent-browser」。**默认不该切，除非命中第 4 节的例外**。
> 事实基线：2026-11 对 Midscene `--bridge` 模式的调研，取证方式为官方文档站 `midscenejs.com`、官方 skill 文档（GitHub `web-infra-dev/midscene-skills`）、unpkg 上发布的 dist 产物源码、以及 CLI 帮助文义。命令细节以其自带文档为最终权威。

## 1. 定位差异

| 维度         | agent-browser                                          | Midscene `--bridge`                                           |
| :----------- | :----------------------------------------------------- | :------------------------------------------------------------ |
| 谁做决策     | 调用方（人或 agent）读无障碍快照后显式指定元素         | VLM 看截图自行决定点哪里、点几下                              |
| 命令粒度     | 细粒度原子命令（`open`/`click`/`fill`/`tap --locate`） | 粗粒度意图（`act "在搜索框输入 X 并回车"`），内部是模型子循环 |
| 单命令延迟   | 亚秒级到数秒，取决于页面等待策略                       | 官方自述典型约 1 分钟/条                                      |
| 跨命令状态   | 守护进程常驻，session 内状态连续                       | 一进程一条命令，命令结束即销毁，靠浏览器进程常驻续接          |
| 需要模型 key | 不需要，零模型调用                                     | 必需，OpenAI 兼容 chat/completions 端点                       |

一句话记法：agent-browser 是**你指挥的机械臂**（每一步谁动、动哪里都由你定，可复现）；Midscene 是**你说需求、它自己看屏幕的实习生**（省心，但路径不可控、按次计费）。选哪个取决于你要的是「可控」还是「省写」。换来的代价不同，别把两者当同一层的替代品。

## 2. 已核实的关键事实

- **一进程一条命令**：每条命令结束即 `tools.destroy()` 断开；跨命令之所以还能续上，靠的是「浏览器进程 / 标签页常驻」，不是 CLI 会话。`[官方文档]`
- **Bridge 模式下 CLI 是 WebSocket server**（默认 `127.0.0.1:3766`），**Chrome 扩展是 client**；`--bridge` 与 `--cdp` 互斥，二选一。`[官方文档]`
- 官方自述**典型一条命令约 1 分钟**，并明确要求**不要后台运行、一次只跑一条命令**。`[官方文档]`
- `act` 不是原子点击，而是「给一句话、模型自己点 N 下」的子循环；真正原子的只有 `tap --locate`。`[源码核对]`
- **没有 tab 切换命令**：只能「开新 tab」或「连当前 tab」，无法在已有 tab 之间来回切。`[官方 CLI 帮助]`
- 模型层是标准 **OpenAI 兼容 chat/completion**，**core 里没有 Ollama 专用适配器**；不装 Ollama 不影响使用。`[源码核对]`
- **零付费路径只在特定前提下唯一**：**在没有本地 GPU、也不打算装 Ollama 的前提下**，唯一现实的零付费路径是**免费层的云 VLM**（如 Gemini 免费层），代价是**截图出境 + 免费层数据可能被用于改进产品 + 限速**。`[官方文档 + 推理]`
- **本地推理是另一条零 API 费路径**：若有本地 GPU 或愿意跑本地推理，本地 Ollama/vLLM 跑 UI-TARS、或自托管 AutoGLM-9B（core 无 Ollama 专用适配器，但可经 OpenAI 兼容端点接入），不产生 API 费用（成本转为硬件与调试）。`[官方文档 + 推理]`

## 3. 由上述事实直接推出的工程结论

- **「跨命令状态」续的是浏览器，不是 CLI 会话**：上一条命令的上下文、变量、输出都不在，想要「接着上一步的句柄」必须自己靠页面状态重建。
- **`--bridge` 与 `--cdp` 互斥**：Windows 上常用的「CDP 接管已有 Chrome」链路与 bridge 不能同时启用，排障时别指望两者叠加。
- **1 分钟/条 × 一次只跑一条**：20 步流程就是 20 分钟量级，这个时间成本要在任务规划阶段算进去，而不是跑到一半才发现。
- **没有 tab 切换**：多标签流程必须在 agent-browser 侧先规划好窗口/标签结构，Midscene 补不了这个位。

## 4. 决策树

| 你的真实需求                                  | 选择                                                  | 理由                                                 |
| :-------------------------------------------- | :---------------------------------------------------- | :--------------------------------------------------- |
| 逐动作精确编排、需要可复现、零模型成本        | **agent-browser**                                     | 原子命令 + `@eN` 引用，同输入同输出，无采样随机性    |
| 一句话完成复杂页面操作，且能容忍 1 分钟级延迟 | 才考虑 **Midscene**                                   | 用延迟和费用换「不用写每一步」                       |
| 只是要可视化体感（光标会动、元素高亮）        | **agent-browser**，`--input-mode human` + `highlight` | 观感需求不是 VLM 需求，用视觉模型属于杀鸡用牛刀      |
| 页面是重 WebGL / Canvas，DOM 与无障碍树不可达 | **Midscene**（VLM 兜底）                              | 在本文讨论的这两个方案之间，VLM 是当前唯一可行的兜底 |

判断顺序固定为：**先问是否可复现、再问是否 DOM 可达、最后才问是否愿意为每步付费**。任一条为「否」即停在 agent-browser。

## 5. 反模式

- **为了「看起来更智能」引入 VLM**：结果是每步都产生模型费用，且同样输入两次跑出不同路径，验收结论无法复现。
- **把 Midscene 当原子命令执行器**：误以为 `act` 只点一下，实际它跑的是多步子循环，超时与重试逻辑全部失控。
- **在无模型 key 的环境里跑 Midscene**：卡在握手 / 鉴权阶段，误判为「浏览器启动失败」，浪费一轮排障。
- **用 Midscene 替代 `highlight` / `--input-mode human`**：把「给人看的可视化」错当成「给模型看的理解」，纯增成本。
