# 案例集：进程、会话与残留治理

> use-agent-browser 技能参考层。案例均来自真实项目实战复盘（已脱敏）。共同主题：**agent-browser 及其拉起的浏览器是真实消耗资源的进程，归属判断与清理边界必须基于证据**。命令语法以 `agent-browser skills get core` 为最终权威。疑似残留进程的审计与清理遵循 `cleanup-agent-team-node-processes` 技能（如已安装）；本文件只沉淀判断依据。

## 案例 1：agent-browser 进程拓扑与 prewarm 池

- **现象**：任务管理器中出现大量 node 进程与多个 `agent-browser-win32-x64.exe`，疑似泄漏。
- **根因**：经全链取证，进程树为 `宿主应用 → sidecar → MCP server → cmd.exe → node agent-browser.js mcp --tools all → agent-browser-win32-x64.exe`——agent-browser 是 Electron 应用，**每个 node 端实例拉起一个独立 Chromium**；多个实例来自宿主的多个 prewarm 池，是设计代价而非泄漏（实测约 80 进程 / 1.6 GB 量级）。
- **关键误导点**：按进程数量判断泄漏；不了解「一个实例 = 一个独立 Chromium」的成本模型。
- **有效修复**：不做清理，先按命令行指纹归类归属；若要降低占用，关闭非活跃 prewarm 池但**保留当前对话 attach 的那个**（否则新对话会重新 spawn）。
- **验证方式**：按 PPID 链逐层溯源到宿主 daemon，每个进程可解释。
- **后续约束**：数量多只触发审计，不能证明泄漏或空闲；清理决策必须回到单次不可变进程快照的归属证据。

## 案例 2：循环批量拉起 GUI 进程 = 卡死

- **现象**：agent 循环执行 10 条「拉起 GUI 应用」的 CLI 命令，2 分钟内新增约 41 个进程，机器卡死。
- **根因**：每条命令都拉起一个带 GUI 的重型进程；循环批量调用使成本线性叠加。
- **关键误导点**：单条命令「看起来很快」，没有意识到它的进程成本模型。
- **有效修复**：立即静默停止批量操作；对 agent-browser 同理——每个实例一个独立 Chromium，**禁止循环批量启动**，并避开用户开发时段。
- **验证方式**：停止后资源恢复；改为逐条、按需、用完即收的方式执行。
- **后续约束**：任何「每实例一个重型子进程」的 CLI（浏览器、IDE、模拟器）都不进循环。

## 案例 3：浏览器实例登记与收口红线

- **现象**：可见 Chrome/CDP 验收、临时 Chrome profile、remote debugging port 在超时或脚本失败后残留，端口与 profile 无人认领。
- **根因**：启动时未登记，失败路径没有 finally 清理，结束前没有复查。
- **关键误导点**：「验收脚本成功了」就等于「环境干净了」。
- **有效修复**：本机接管的实例启动时登记 `--remote-debugging-port`、`user-data-dir`、PID、owner 与关闭策略；脚本用 `finally` 清理；任务结束执行 `agent-browser close` 并复查端口/PID/profile/临时截图。
- **验证方式**：结束前复查清单逐项为空；按会话标识审计无残留进程。
- **后续约束**：只能关闭自己启动或明确获得授权的浏览器实例；先做最小 smoke 再扩大矩阵，降低中途残留的暴露面。

## 案例 4：清理边界——MCP 常驻服务不是清理目标

- **现象**：事故进程清理时，机器上同时存在 memorix、codegraph、agent-browser 等多个 MCP 服务进程；处理事故时容易被顺手一起清掉。
- **根因**：MCP 服务是 AI 工具链的长期常驻服务，不是本次任务的临时进程。
- **关键误导点**：按进程名批量清理；把「数量多的 node 进程」一锅端。
- **有效修复**：清理范围只限本次 run 可证明拥有的进程；MCP gateway、记忆服务、监控、队列、SSE、RAG 等长期服务列入排除规则；高风险停止先人工确认。
- **验证方式**：清理后长期服务仍存活，目标 PID 已停止且重采样确认。
- **后续约束**：具体门禁、归属证据要求与 WorkBuddy 池的双确认规则，见 `cleanup-agent-team-node-processes` 技能；本技能只负责「验收后收口自己的会话」。

## 案例 5：无头会话后的归属误判

- **现象**：无头自动化会话结束后审计，发现大量 Node/MCP 进程，容易被归因为「本次会话的残留」。
- **根因**：这些进程实际是其他环境的长期 MCP/工具服务（含 agent-browser 运行时），与本次会话无关。
- **关键误导点**：把「同时出现在机器上」当成「由我产生」。
- **有效修复**：按 scoped 归属审计下结论——只对能回到 runId/sessionId/PPID 链/命令行指纹多个证据点的进程判定归属；结论明确标注为「本次 scoped 运行后的归属审计」，不做泛化归因。
- **验证方式**：审计输出中每个保留进程都有归属解释。
- **后续约束**：单一线索（如进程名含 agent 关键词）只能记为待审计，不能作为清理依据。

## 案例 6：配置声明 ≠ 运行时拉起

- **现象**：MCP 配置文件声明了 agent-browser 等 7 个服务且全部 `enabled: true`，但运行时既无对应子进程也无状态记录——工具全部不可用。
- **根因**：配置文件只是声明；实际拉起取决于宿主运行时，可能因 trust 审批、`NODE_OPTIONS` 注入（宿主给子进程注入的 `--use-system-ca` 等参数会破坏部分 Node 子进程启动）等原因静默失败。
- **关键误导点**：看到配置正确就认为「应该已经生效」。
- **有效修复**：四层下钻排查：磁盘配置 → 运行时状态库 → 主进程子进程列表 → MCP 服务自身日志；对注入类根因，显式覆盖 `NODE_OPTIONS` 环境变量。
- **验证方式**：下钻到具体层定位失败原因，修复后子进程可见、工具可用。
- **后续约束**：「MCP 工具不可用」的第一动作是确认**运行时有没有真的拉起**，而不是反复改配置文件。

## 案例 7：会话与进程的三态归属

- **现象**：判断一个 agent-browser/浏览器进程「是否属于当前会话」时，只有创建时间较旧、最近无新子进程等弱信号。
- **根因**：弱信号无法证明会话归属或空闲状态。
- **关键误导点**：用「进程年龄 + 最近没动静」推断僵尸。
- **有效修复**：归属判定用三态：`current`（有明确归属证据）/ `not-current`（有明确非归属证据）/ `unknown`（证据不足）；`unknown` 只审计不清理。
- **验证方式**：清理决策仅落在 `current` 且已确认空闲的实例上，重采样确认结果。
- **后续约束**：证据缺失时降低置信度而不是补一个结论；「宁可不清理，不可误清理」。
