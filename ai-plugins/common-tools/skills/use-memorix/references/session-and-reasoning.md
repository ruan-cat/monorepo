# 会话、交接与推理记录

本文件处理 session 生命周期、跨上下文交接与 reasoning 记录。记忆条目本身的读写见 memory 域。

## 读写分区

| 动作                       | 性质 | 授权       |
| :------------------------- | :--- | :--------- |
| `session context` / resume | 只读 | 自动       |
| `session start`            | 写入 | 创建前确认 |
| `session end`              | 写入 | 结束前确认 |
| handoff / receipt          | 写入 | 生成前确认 |

- 恢复会话只读不写：读取 `session context`，把目标、状态、下一步拿回来即可。
- 项目绑定硬门。活动会话存在不能跳过 MCP 根目录核对。不一致时先确认，再把当前工作区绝对路径传给 `projectRoot`。
  1. 在当前工作区运行 `memorix session context`，记下 CLI 项目 id 和根目录。
  2. 读取 MCP `memorix_project_context`，记下它绑定的项目 id 和根目录。
  3. 两边都必须等于当前工作区。CLI 报本项目已有活动会话，不能代替这次核对。
  4. 有一边不是，停止 `memorix_store` 和 `memorix_resolve`。向用户展示两边的项目 id 与根目录，确认后第一件 MCP 调用才是 `memorix_session_start`，`projectRoot` 传当前工作区绝对路径。
  5. `session_start` 会关闭该项目上一个活动会话。确认前不调用。
  6. 绑定成功后再次核对。仍不一致就停止，不写。
  7. 只有 `session_start` 失败，才走 CLI 兜底。CLI 的工作目录必须是当前工作区。
- `end` 会写结束状态与摘要；结束前确认摘要内容，不要写入未经证实的结论。
- handoff 是写操作，且通常是长任务唯一可靠的跨上下文载体；内容必须可核对。

## 收尾时没有活动会话

1. 先跑只读的 `memorix session context`。回复里写上活动会话数量，以及最近一条已结束会话的代理和时间。命令失败时原样报失败，不把它说成 `0 active`。
2. 写明本对话有没有调用过 `session start`。没调用过，就写「本对话没有活动会话」，不得写「我的会话被其他代理关掉」。
3. `0 active` 不是索引错误，也不是归档失败。没有活动会话时，MCP 写入不可用；只读 `session context` 仍然有效。
4. 这一轮只问一件事：要不要新建会话，以便之后写入。不同时确认 `store`、`session end`、handoff 或 `archive`。
5. 用户说不存储、不启动或不归档：不调用 `session start`，不写入，不进入归档。
6. 只有本对话曾经 `session start` 成功，之后的只读结果变成已结束，且结束记录属于其他代理，才可以写「可能被其他会话结束」。三样缺一样，就写「本对话没有活动会话」。
7. 归档是否成立只看 retention 域的候选硬门。没有活动会话不是归档失败。

## handoff 结构

一份合格的 handoff 至少包含：

1. 目标：这次任务要达成什么，非目标是什么。
2. 当前状态：已完成、进行中、未开始，逐项标注。
3. 关键决策与理由：为什么这样选，放弃了什么。
4. 证据：命令、文件路径、测试名、SHA、CI 结果。
5. 下一步：下一个人接手应先做什么，禁止做什么。
6. 阻塞与风险：已知失败、待确认项、不可逆操作。

写法要求：

- 用可复现的事实，不用「应该没问题」。
- 路径写仓库相对路径；不写用户主目录、临时目录或凭据。
- 交接文件更新是写操作：只回填事实，不改写历史结论。
- 长任务跨多轮上下文时，以 handoff 为唯一进度事实源；对话记忆只作补充。

## reasoning 记录

- `reasoning` 类型用于记录判断链与取舍，不用于流水账。
- 需要复盘「为什么当时这么决定」时优先写 reasoning；需要复盘「改了什么」写 what-changed。
- 官方提供更强的 reasoning 审阅与长期记忆能力时，路由官方技能，不在本技能复制其步骤。

## 路由官方技能

| 场景                                    | 路由                           |
| :-------------------------------------- | :----------------------------- |
| 需要完整会话协议、receipt、复杂恢复流程 | 官方 `memorix-sessions`        |
| 需要 reasoning 审阅、推理链评估         | 官方 `memorix-reasoning`       |
| 需要 team 协作、多 agent 编排           | 官方 `memorix-orchestrate`     |
| 需要 long-term 沉淀、promote 流程       | 官方 `memorix-memory`          |
| 需要跨项目/跨库迁移（transfer）         | 官方 `memorix-sessions`        |
| 官方技能不可用                          | 本文件兜底，并声明这是简化流程 |

## 失败分支

| 现象                              | 处理                                                                                         |
| :-------------------------------- | :------------------------------------------------------------------------------------------- |
| 恢复后上下文明显缺失              | 重新取 `session context`，检查项目绑定与 handoff 路径                                        |
| `start` 报已存在 active session   | 先确认是否应复用或结束旧会话，不强制新建                                                     |
| handoff 写入被拒                  | 检查当前命令是否暴露该子命令，读 `--help` 后再说                                             |
| 交接内容与仓库状态不一致          | 以 `git status` / 测试输出为准，修正 handoff 再继续                                          |
| `session context` 显示 `0 active` | 按「收尾时没有活动会话」回复。不推断竞态，不把索引或归档说成失败。这一轮只确认要不要新建会话 |

交接不是免责声明：写进 handoff 的「已完成」必须有对应证据，否则标为「未验证」。
