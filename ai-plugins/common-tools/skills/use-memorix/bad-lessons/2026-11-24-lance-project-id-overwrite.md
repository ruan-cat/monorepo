## 代码怎么让覆盖发生

Lance 这张表给所有项目共用。写入用 `mergeInsert`，键只有 observation id，匹配到就整行更新。同一个数字编号后来再写一次，后一次的 `project_id` 会盖住前一次，不会为另一个项目再留一行。

内存里等待刷盘的批次已经用「项目：编号」当键。刷进 Lance 时，持久化合并把项目这一段丢掉了。

「这个编号是不是已经有向量」也只收集数字编号。common 占着 6468 时，monorepo 的补写会认为 6468 已经有向量，于是跳过。搜索又按项目过滤，标错的行对 monorepo 不可见。于是正文在，向量也在，当前项目的向量查询看不见。

一次正确的 monorepo 存储，本应把 Lance 的 `project_id` 写成 monorepo。表上的结果是 common。合并键允许后一次写入盖住整行。写作时没有一条日志能指出是哪一个进程用 common 的身份写了这四个编号。能确定的是：这种覆盖在当时的合并键下会发生，而且覆盖之后，搜索和补写都会跟着错。

缓存日志 `Loaded N cached API embeddings` 数的是 API 向量缓存的条数，不是 Lance 行数，也不是记忆条数。这次缓存从大约 1671 涨到 1678 之后，整词开始能中。中文短句在缓存已经补上时仍然看不见这四条。多等缓存解决不了分区写错。

## 修复动了哪一层

上游拉取请求 410 改的是以后怎么写入。

- 合并键改成 project id 加 observation id。两个项目可以各有一行相同编号。
- 写入某个项目的编号时，如果已经存在同一编号、项目号却不同的旧行，先删掉再写。没有这种冲突行就不删。
- 「已经有向量」改成看「项目：编号」。别的项目占着同一个数字，不再挡住当前项目补写。

它不改打分，不改 fuzzy 的规则，也不改 embedding 模型。它也不改写用户机器上已经标错的 6468–6471。修复进了正在运行的安装包之后，这四行仍然要单独重写或删除，monorepo 的向量查询才会看见它们。

写作时该请求还没合并。随修复提交上去的测试，是在临时表里先把同一编号写成 common，再写成 monorepo，然后检查每个项目只能看见自己的那一行。Ubuntu 和 Windows 上这轮测试通过。macOS 那次运行在排队时被取消。没有上游仓库的管理员权限，不能代为重跑。
