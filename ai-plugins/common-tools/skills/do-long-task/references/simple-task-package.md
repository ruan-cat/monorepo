# 简易任务包

本文件只适用于同目录具备 `spec.md`、`plan.md`、`handoff.md` 的短周期任务包。预期执行时间大约 30 分钟到 1.5 小时，通常一次上下文就能做完。它不是 OpenSpec change，不要套用 `tasks.md`、`proposal.md`、`design.md`、`specs/`、`agent-progress.md` 或 `agent-findings.md`。

## 识别

同时满足下面三条，才是简易任务包：

1. 用户给出的目录，或当前工作目录，里面有同级的 `spec.md`、`plan.md`、`handoff.md`。
2. 该目录不是 OpenSpec change。OpenSpec change 位于 `openspec/changes/` 或 `openspec/changes/archive/` 下，并拥有自己的 `tasks.md`。
3. 用户要执行、续跑、交接、验收，或为这个目录生成长任务提示词。

目录名里出现 `docs/plan`、`docs/prompts`、`docs/one-use`、任务包、交接，只能帮助识别，不能代替这三份文件。

判定冲突时，以用户点名的那个目录为准。点名的是 OpenSpec change，就走 OpenSpec。点名的是三文件目录，就走本文件。仓库里另外存在 OpenSpec change，不改变这个判定。

三份文件缺任何一份：指出缺哪一份，停止执行。不要补造 OpenSpec 目录，也不要擅自新写缺失的那一份来冒充任务包，除非用户明确要求补齐工件。

只谈方案、还没要求执行：不要进入执行模式。

## 三份文件的职责

| 文件         | 职责                               | 什么时候改                               |
| ------------ | ---------------------------------- | ---------------------------------------- |
| `spec.md`    | 合同：目标、非目标、验收、冻结接口 | 验收、可见行为或冻结合同变化时，先改这里 |
| `plan.md`    | 唯一可执行任务源                   | 开始、完成、补遗漏任务时                 |
| `handoff.md` | 唯一状态和证据文件                 | 任务边界、暂停、阻塞、完成时             |

`handoff.md` 不是第二份任务清单。聊天 checklist、子代理报告和临时计划都不是任务源。

## 使用顺序

1. 读 `handoff.md` 的状态、依赖门、授权门、阻塞、证据回填，以及执行者下一条命令。这些内容先当作上次记录，不当作当前事实。
2. 按下面的接手复核，重跑 handoff 自己写明的第一条命令或最小预检。易腐栏与仓库不一致时，先原位改正 handoff，再决定能否做 Task。
3. 门未满足，或复核结果改变了门的含义时，停止。不要绕过 handoff 已写明的门。
4. 读 `spec.md` 的目标、非目标和验收。非目标里的工作不做。
5. 读 `plan.md` 的全局约束，只选复核后仍然有效的那一个未完成 Task。handoff 没有指向时，选计划中的第一个未完成 Task。
6. 确认该 Task 的修改范围、验收和验证命令。
7. 做这一 Task 的最小改动。
8. 运行该 Task 写明的验证。没有命令时，把替代验证和剩余风险写进 handoff，不能写成通过。
9. 用新证据原位替换 handoff 的对应易腐栏，再把该 Task 标成完成。
10. 把下一条命令改成对着当前仓库能重新执行的命令。
11. 进入下一 Task 前，重新读这三份文件里刚改过的部分。

一次上下文通常够用，所以不要为了防压缩额外拆夜班或新建 checkpoint 文件。暂停、阻塞或换会话前，易腐栏必须已经改成当前结果。下一位先复核，复核通过后才按文件续上。

## 维护规则

- 三份文件保持同级，不改名、不日期化、不拆走。
- 沿用 `plan.md` 已有的完成标记。没有标记时，在对应 Task 标题下写一行 `执行状态：未开始`、`进行中` 或 `已完成`。不要在文首另起一套清单。
- 属于本包的遗漏工作，先补进 `plan.md` 的对应 Task 或新 Task，写清原因和验证，再做。
- 验收或冻结合同变了，先改 `spec.md`，再改 `plan.md`。技术路线变了，同步 spec 里的合同和 plan 里的任务，不另开设计文件。
- `Global Constraints`、冻结接口、禁止动作、非目标，在用户改合同之前保持原样。
- handoff 分成两类栏，更新方式不同。
- 耐久栏：门禁、授权、禁止动作、回滚顺序、允许范围。只在合同变化时改。事实复核不得顺手改写这些栏。
- 易腐栏：状态、当前 Task、分支、HEAD、dirty、index、SHA、文件哈希、证据、阻塞、下一条命令。每次接手和每个 Task 边界都原位替换。栏位标题按文件里的实际标题匹配。
- 同一类当前状态只留一处。文末又出现第二份状态时，合并回原来的状态栏，删掉重复节。
- handoff 没有状态或下一步栏时，在文末追加一节 `## 执行状态`，只写当前 Task、状态、核对命令、核对结果、阻塞、下一条命令。不重写全文。
- 证据写命令、结果、提交或文件位置，并写上这次核对的时间。完整日志留在命令输出或该 Task 已指定的证据文件。
- 旧结论被新命令推翻时，替换单元格里的当前值，并在该栏留一行 `作废：<旧值>；原因：<命令与结果>`。作废行不能再被当成下一步。已经标成历史的段落只保留追溯，不提供下一条命令。
- 计划写完成时，handoff 必须有尚未过期的对应证据。handoff 写完成但没有证据、证据命令无法复跑，或复跑结果与记录不符，都视为未完成。
- 不创建 `agent-progress.md`、`agent-findings.md`、`tasks.md`、`proposal.md` 或第二份 plan。
- 不把简易包改写成 OpenSpec change，除非用户明确要求升级成隔夜 OpenSpec 任务。

## 接手复核

每次启动、续跑、上下文恢复后，先复核再实现。handoff 记录的是上次看到的仓库，仓库一提交、一改文件，里面的 SHA、dirty、哈希和“已完成”就会过期。

复核顺序：

1. 运行 handoff 写明的第一条命令。它没写时，至少运行 `git status --short --branch`、`git rev-parse HEAD` 和 `git branch --show-current`。
2. 把结果与易腐栏对比。一致才采纳状态、证据和下一条命令。
3. 不一致时，handoff 的易腐栏算过期。用新结果原位替换，保留一行作废原因。然后重新判断门是否仍成立。
4. 复核涉及用户或其他代理已有改动时，只更新基线记录。不 reset、checkout、stash，也不覆盖那些文件。基线冲突改变了任务范围或门的含义时，停止并问用户。
5. 文件表或哈希栏写着“实施前必须重算”时，使用对应文件之前先重算。对不上就先改正表格。

三份文件冲突时按这个顺序取舍：当前命令结果决定事实，`spec.md` 和 `plan.md` 决定还要做什么，`handoff.md` 只保存上一轮信念。handoff 与新鲜命令冲突时改 handoff。handoff 把计划里的未完成 Task 写成完成时，以计划为准，直到新证据出现。

## 失败与停止

验证失败时，在 handoff 记下失败命令、结论和不能再走的路径，然后换方案。不要把同一失败重复记成新任务。

只有这些情况才停下问用户：权限不足、破坏性操作、需求互相冲突、产品决定，或同一失败连续 3 次。其他情况做完当前 Task 后直接进入下一个。

停止时 handoff 必须包含：停在哪个 Task、已有证据、阻塞原因、下一条命令。

## 完成前

- `spec.md` 的验收已经满足，或未满足项已写在 handoff。
- `plan.md` 里声称完成的 Task 都有 handoff 证据。
- 相关验证已经运行，或替代验证和剩余风险已经写明。
- 三份文件仍然同级，且没有新的进度文件。
- 没有未解决的阻塞被写成完成。

## 提示词生成

用户只要求为简易包生成 Claude Code `/goal`、Codex `/goal` 或 do-long-task 提示词时，使用 `references/codex-goal-prompt.md` 的简易包模板。生成时不修改三份文件，不创建进度文件，不跑验证。
