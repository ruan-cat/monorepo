# prettier-plugin-lint-md 版本矩阵

## 现行结论

精确安装 `prettier-plugin-lint-md@1.0.1`。必须同时核验 `package.json`、lockfile 和运行时解析版本；任何 semver 范围都不算锁定。

| 版本    | 包入口特征                   | 顶层字符串在普通 CLI | 顶层字符串在 experimental CLI | 顶层字符串在 VSCode | 状态   |
| ------- | ---------------------------- | -------------------- | ----------------------------- | ------------------- | ------ |
| `1.0.1` | ESM `.js` 主入口             | 生效                 | 生效                          | 生效                | 现行   |
| `1.0.3` | CJS `main`，另有条件 exports | 生效                 | 生效                          | 可能静默失效        | 已废弃 |

## 为什么 `^1.0.1` 是错误锁定

`^1.0.1` 允许包管理器解析 `1.0.3`。依赖字段仍显示从 `1.0.1` 开始，容易让审计者误以为项目正在运行已验证版本；真正执行的却是 lockfile 和 `node_modules` 中的 `1.0.3`。

必须检查三层：

1. 声明层：`package.json` 必须是精确字符串 `"1.0.1"`。
2. 解析层：lockfile 对当前 importer 的快照必须解析为 `1.0.1`。
3. 运行层：从实际命令执行目录解析到的包元数据必须报告 `1.0.1`。

## 1.0.3 静默失效边界

VSCode Prettier 扩展会从顶层字符串解析插件入口。`1.0.3` 的 CJS 入口在动态导入后可能形成嵌套 default，Prettier 没有拿到预期插件对象和选项。结果不是明确报错，而是 Markdown 保持原样，因此只看“格式化成功”会产生假绿。

不要把对象插件作为 `1.0.3` 的补丁。对象能绕过 VSCode 的字符串解析，但 experimental CLI 不接受对象 specifier。正确处理是回到经完整矩阵验证的 `1.0.1` 顶层字符串。
