# 2026-08-31 双 Qoder 会话并行重载导致机器 CPU 饱和

## 1. 问题现象

同一台机器上同时运行两个 Qoder 会话：会话 A 执行 install-mcp 技能升级与发布准备，会话 B 执行 install-skills / sync-local-global-agents-skills 升级与 118 个 skills 的目录级链接重建。用户反馈整机 CPU 被用完、系统明显卡顿。

## 2. 实际根因

CPU 不是被「等待/监听另一个会话」这个动作本身吃掉的，而是三类负载叠加：

- 两个 Qoder 会话的工具链并行运行：会话 B 正在跑 vitest 全量测试、tsx、prettier 与 118 个 skills 的目录级链接替换（大量文件系统操作）；会话 A 前期也运行了 prettier、Node registry 生成器、git 与 memorix CLI。
- Qoder（Electron）宿主进程本身：事故时采样榜首进程 `Code`（PID 19480）已累计消耗 8490 秒 CPU。
- 机器上与 agent 无关的后台软件（360ChromeX、QQ、msedgewebview2 等）。

会话 A 的编排失误放大了并行窗口：发现并行会话后没有错峰，而是选择「保持 turn 的内联阻塞等待」（`wait_chat_sessions` 60 秒循环 + 等待间隙插入 git 检查），使会话 A 的运行态在整个等待期一直存活。

## 3. 关键误导点

- 第一直觉容易把原因归为「监听机制在忙等耗 CPU」。实际 `wait_chat_sessions` 是事件驱动的阻塞等待（60 秒超时上限），本机开销接近零；等待机制不是 busy loop。
- 另一个误导点是以为「本会话静默 = CPU 立刻归零」。会话 A 静默后 node 进程从 16 降到 7，但 `Code` 主进程仍新增累计 +2752 秒——那是用户选择保留的会话 B 在继续工作，不是会话 A 的残留。

## 4. 有效修复

- 立即停止所有 `wait_chat_sessions` 轮询与 git 检查，会话 A 进入完全静默（不再发起任何命令）。
- 发布编排改为「用户触发式交接」：会话 B 完成后由用户说一声「发布」，再一次性执行合并发布。
- 不杀会话 B 的进程：它正处于目录级链接替换关键步骤，强杀会把 `~/.qoder/skills` 置于半替换状态。

## 5. 验证方式

进程采样对比（PowerShell `Get-Process | Sort-Object CPU` + node 进程计数）：

- 事故时：node 进程 16 个；`Code`（PID 19480）累计 8489.9 秒。
- 会话 A 静默后：node 进程 7 个；同 PID 累计 11241.7 秒（增量为保留的会话 B 持续工作所致）。
- 会话 A 静默后未再发起任何新命令。

## 6. 后续约束

1. 需要等待另一个会话的产物时，默认「结束当前 turn，交给用户触发」；禁止保持 turn 做内联阻塞等待。
2. 并行调度重载命令（测试、构建、registry 生成、批量文件操作）前，先确认机器是否已有其他重载会话；必要时先错峰并向用户说明。
3. CPU 饱和窗口内不再发起任何命令；取证仅限一次性轻量采样。
4. 发现另一会话正在执行批量文件系统变更（软链接重建、目录替换）时，不要杀其进程；强杀会留下半完成目录状态。
5. 归因必须事实驱动：等待机制接近零开销，吃 CPU 的是并行工具链——不赖 busy loop，也不甩锅环境。
